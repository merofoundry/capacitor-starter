# MeroFoundry Capacitor starter

A native iOS and Android shell for an application hosted on MeroFoundry. By default (remote
mode) the app loads your application's own site over HTTPS (`https://<host>`), so the login
pages, the `/api/` surface and the cookie session work exactly as they do in a browser.
Activating a new site version updates every installed app on its next launch; only native
changes need a store resubmission. In bundled mode the app instead packages a copy of your
already-built site (see [1. Configure](#1-configure)).

You own everything here: the developer accounts, the signing material, this repository and
the CI that builds and uploads the apps. MeroFoundry never builds or submits an app for you,
and nothing in this project uses a MeroFoundry credential.

## What the shell adds

- Launch screen, app icons and splash screens generated from two images.
- An offline screen with **Try again** when the host cannot be reached. It is bundled in
  the app, so it works with no network and without any Capacitor plugin.
- A settings screen with the app version, shell version, host, whether notifications are on,
  app lock switch and **Sign out**.
- An optional app lock (Face ID, Touch ID, Android biometrics or the device passcode) on
  launch and whenever the app returns from the background.
- Safe-area CSS variables and status-bar handling for the hosted site.
- The native share sheet and haptics, through the official `@capacitor/share` and
  `@capacitor/haptics` plugins.
- Pull to refresh at the top of your site's pages, on Android and iOS. It is built into the
  starter itself, not a Capacitor plugin (see [Pull to refresh](#pull-to-refresh)).
- Deep links: `https://<host>/...` opened on the device opens the app at that path, once
  you publish the association files (see [Deep links](#deep-links)). Links to any other
  host are ignored.
- Provider sign-in (Google, GitHub, Microsoft) through the operating system's
  web-authentication session, shown to your site only when the device and your application
  both support it (see [Provider sign-in](#provider-sign-in)).
- Push notifications through APNs and Firebase Cloud Messaging, turned on by your site and
  opened at the notification's path (see [Push notifications](#push-notifications)).

## Layout

```
starter.config.json        host, appId, appName, mode and site: the only values you edit
capacitor.config.ts        builds the Capacitor configuration from starter.config.json
www/                       NOT committed: assembled by `npm run web` (see below)
android/                   the Android project (committed)
ios/                       NOT committed: generated by `npx cap add ios` (see below)
shell/                     the bundled shell screens: offline, lock, settings (plain HTML/CSS/JS)
native/shell-bootstrap/    the shell's native code for both platforms (local to the starter)
assets/icon.png            1024×1024 or larger, square, no transparency needed
assets/splash.png          2732×2732 or larger, square, logo centred
scripts/, lib/             web and artwork preparation, iOS preparation and the release guard
fastlane/Fastfile          the iOS signing and TestFlight lane
.github/workflows/         ios.yml and android.yml release workflows
test/                      `npm test`
```

## 1. Configure

Edit `starter.config.json`:

```json
{
  "host": "app.example.com",
  "appId": "com.example.app",
  "appName": "Example App"
}
```

- `host` is the bare host name your application is served on, without `https://`, a port
  or a path. The app may navigate on that host only. Cleartext HTTP and mixed content are off.
- `appId` is your iOS bundle identifier and Android application id.
- `appName` is the name under the icon.
- `mode` is optional: `"remote"` (the default when omitted) or `"bundled"`.
  - `remote`: the app loads `https://<host>`, your hosted site.
  - `bundled`: the app packages your already-built site and serves it from the device
    (`capacitor://localhost` on iOS, `https://localhost` on Android). `host` stays the
    application host your site's API calls reach; your application's allowed origins must
    list those two origins.
- `site` is required in bundled mode and refused in remote mode: the path, relative to this
  directory, of your **already-built** site, a readable directory with an `index.html`, for
  example `"../my-site/dist"`. It must not be or contain `www/`. The starter copies it as it
  is; it never builds your site, so build it first.

```json
{
  "host": "app.example.com",
  "appId": "com.example.app",
  "appName": "Example App",
  "mode": "bundled",
  "site": "../my-site/dist"
}
```

`npm run web` assembles `www/`, the directory Capacitor packages, in both modes: the shell's
own screens go to `www/meroshell/`, and in bundled mode your site is copied to the `www/`
root. The `meroshell/` path is reserved for the shell, so a site with a top-level `meroshell`
file or directory is refused. `www/` is generated and not committed; run `npm run web` before
`npx cap add ios` and before every `npx cap sync`, and again whenever your site changes. (Every
`npx cap sync` and `npx cap copy` also reassembles it first.)

Replace `assets/icon.png` and `assets/splash.png` with your own artwork. Then:

```sh
npm ci
npm test
npm run web
```

Every value derives from `starter.config.json`: the Capacitor configuration, the Android
application id, label and App Links host, and the iOS bundle id, display name and associated
domain. The WebView's user agent ends in `MeroFoundryShell/<starter version>`. Capacitor's own
bridge logging is off in both modes, so plugin calls (such as the session tokens below) are
never written to the device log.

## 2. Android

`android/` is committed. Generated artwork and copied web assets are not, so prepare them
before opening the project:

```sh
npm run web
npx cap sync android
npm run assets -- --android
npx cap open android
```

## 3. iOS

`ios/` is never committed. Generating it needs Xcode, so it is created on your Mac or on the
macOS runner, and the iOS workflow creates it again on every run. Assemble `www/` first, then
**the first iOS project step is `npx cap add ios`**:

```sh
npm run web
npx cap add ios
npx cap sync ios
npm run ios:prepare
npm run assets -- --ios
npx cap open ios
```

`npm run ios:prepare` applies the starter's iOS customizations to the generated project:
the Face ID usage text, the display name and bundle id, the `applinks:<host>` associated
domain, and a build phase that runs the release guard on every non-Debug build. It is safe to
run again. Make any further iOS change in `scripts/prepare-ios.cjs` and `lib/ios-project.cjs`,
not in `ios/`, so that every fresh generation gets it.

## Preview builds

To point a **debug** build at your preview host, sync with an override:

```sh
npm run web
MEROSHELL_PREVIEW_HOST=preview-app.example.com npx cap sync android
```

In bundled mode the override changes the application host your bundled site is told about and
may navigate to; the site itself still comes from `www/`.

A preview build can never be released. Both workflows refuse to start when
`MEROSHELL_PREVIEW_HOST` is set. Independently, the Android release build (`preReleaseBuild`
depends on `meroshellReleaseGuard`) and the Xcode build phase added by `ios:prepare` refuse
to package when the override is set, when the generated Capacitor configuration still
names the preview host or no longer matches `starter.config.json`, or when `www/` or the
platform's copy of it is missing or stale (a changed configuration, or any file of your site
or the shell edited, added or removed since `npm run web`; the check compares content, not
timestamps). Run `npm run web`, then `npx cap sync <platform>` without the override, before a
local release build.

## Hosted-page integration

The shell injects a small script into your application's own pages before the page's scripts
run: in remote mode only into pages on your configured host, in bundled mode only into pages
on the app's local origin. Your site needs no Capacitor dependency.

- `document.documentElement` gets the class `meroshell` and
  `data-meroshell-platform="ios" | "android"`.
- `window.MeroFoundryShell` is defined, and the `meroshell:ready` event fires on `window`:

  ```js
  if (window.MeroFoundryShell) {
    MeroFoundryShell.share({ title: 'Order 42', url: location.href });
    MeroFoundryShell.haptic('LIGHT'); // 'LIGHT' | 'MEDIUM' | 'HEAVY'
    MeroFoundryShell.setStatusBarStyle('DARK'); // 'DARK' | 'LIGHT' | 'DEFAULT'
    MeroFoundryShell.openSettings();
  }
  ```

- `navigator.share` is provided where the WebView lacks it, so a site that already uses the
  Web Share API gets the native share sheet.
- Attributes work without any script of your own:
  `data-meroshell-action="settings"`, `data-meroshell-action="share"` (with optional
  `data-meroshell-share-title` and `data-meroshell-share-url`), and
  `data-meroshell-action="haptic"` (with optional `data-meroshell-haptic`).
- Safe areas: the web view draws under the status bar. Use the CSS variables
  `--meroshell-safe-area-inset-top`, `-right`, `-bottom` and `-left`, which the shell keeps
  up to date with the device's insets:

  ```css
  .meroshell header { padding-top: var(--meroshell-safe-area-inset-top); }
  ```

- The settings screen is opened from the offline screen or by your site. Give your site a
  link to it inside the app, for example in its account menu:
  `<a href="#" data-meroshell-action="settings" class="only-in-app">App settings</a>`.
- `MeroFoundryShell.refresh()` reloads the current page from your host, exactly as pull to
  refresh does.
- `MeroFoundryShell.mode` is `"remote"` or `"bundled"`; `MeroFoundryShell.host` is always the
  application host.
- `MeroFoundryShell.session` keeps a bearer session's token pair in the device's secure
  storage, in both modes: the iOS Keychain (service = your `appId`, available after first
  unlock, this device only) and, on Android, EncryptedSharedPreferences under an Android
  Keystore master key. Every method returns a promise:

  ```js
  await MeroFoundryShell.session.save({ accessToken, refreshToken });
  const pair = await MeroFoundryShell.session.load(); // {accessToken, refreshToken} or null
  await MeroFoundryShell.session.clear();
  ```

  The shell never logs the tokens, shows them on its screens or sends them anywhere but the
  secure store.
- `MeroFoundryShell.push` turns push notifications on and off with the page's own session. See
  [Push notifications](#push-notifications).
- Provider sign-in is a capability, not a given: show your provider buttons inside the app
  only while `data-meroshell-provider-sign-in="on"` is on the root element (or
  `MeroFoundryShell.capabilities.providerSignIn` is `true`). See
  [Provider sign-in](#provider-sign-in).

## Pull to refresh

Pulling down from the top of a page reloads that page from `https://<host>`. Authorized by Rob
on 2026-10-17 as a narrow, starter-local feature: the official Capacitor plugin catalog has no
pull-to-refresh plugin, so the starter implements it in its own code instead of depending on,
or publishing, a plugin. Share and haptics stay on the official `@capacitor/share` and
`@capacitor/haptics` plugins.

How it is built:

- `shell/hosted-integration.js`, the script the shell injects into your pages, recognises the
  gesture and calls `MeroShell.refresh` with the page's URL. The same file is used on Android
  and on an iOS project freshly generated by `npx cap add ios`.
- The `refresh` method of the starter's own bootstrap (`native/shell-bootstrap`, the same
  `MeroShellPlugin` that runs the lock, offline and settings screens) passes the request to the
  shell controller, and drops it if the shell is covering your site.
- `shell/controller.js` reloads the page only while your site is actually on screen: never
  while the lock screen, an unlock prompt or the settings screen is shown, and not from the
  offline screen. The reload always goes to your configured host; a URL on any other host
  reloads `https://<host>/`.
- If the host cannot be reached, the reload shows the offline screen, and **Try again** reloads
  the same page.

There is no general-purpose plugin project, no separate native refresh control, and nothing on
the MeroFoundry platform side.

When a pull counts:

- one finger, starting while the page is scrolled to the very top;
- not inside an inner element that is scrolled down (that element scrolls instead);
- not inside an element marked `data-meroshell-pull-refresh="off"`, for maps, carousels or
  your own drag gestures;
- the finger moves at least 72 pixels down, more down than sideways, and is lifted there.

A light haptic marks the moment the pull is far enough. While pulling, the page's root element
has `data-meroshell-pull="pulling"`, then `"armed"`, then `"refreshing"`, and the CSS variable
`--meroshell-pull-distance` holds the distance pulled, so your site can draw its own indicator:

```css
.meroshell[data-meroshell-pull] header { transform: translateY(calc(var(--meroshell-pull-distance) / 3)); }
```

## Provider sign-in

Google refuses sign-in inside an embedded WebView and Apple expects provider sign-in in the
system's web-authentication session, so the shell never shows a provider's page in its WebView.
When your site starts a provider sign-in, the shell:

1. loads your sign-in link in its own WebView, which sets the browser-binding cookie there;
2. cancels the redirect to the provider and opens that provider URL in the system session
   (`ASWebAuthenticationSession` on iOS, a Custom Tab on Android);
3. accepts the session's return only when it is an `https://<host>` URL with no credentials
   or port whose path is exactly `/api/v1/applications/<application id>/auth/oauth/exchange`,
   and loads that path and its query in the WebView, which redeems the one-time code there.

Only one sign-in runs at a time, and only while your site is on screen: never behind the lock
screen, an unlock prompt, the settings screen or the offline screen. If the user closes the
session, the app simply stays on the page they were on. Any other failure shows the offline
screen, and **Try again** reloads that page. A return that arrives after the app has locked,
after sign-out or after the session was cancelled is ignored.

### When the buttons may show

Provider sign-in is available only when all of these hold. Until then the shell reports it as
off and your site keeps email and password login:

- the device supports it: iOS 17.4 or later (the first version whose session accepts an HTTPS
  callback); on Android, a browser that provides Custom Tabs and, on Android 12 or later, a
  verified App Links association for your host;
- your application's public metadata at `https://<host>/api/v1/applications/public/by-host`
  answers with a valid application id;
- your application's catalog at `https://<host>/.well-known/api-catalog` answers `200` with
  `"mobile_shell": {"provider_sign_in": true}`. This is the field the shell reads; the
  platform is to publish it only while the `mobile_distribution` capability is enabled for
  your application (ADR 2026-10-16 v2, Ruling 8). A platform that does not publish it leaves
  provider sign-in off.

The shell reads the metadata and the catalog once per launch and again after **Sign out**,
and keeps nothing across launches. It fails closed: if the catalog is not published, or
answers anything but `200`, or the field is missing or not `true`, or the host cannot be
reached, provider sign-in stays off for that launch. If a later read turns it off, the shell
removes it from the page that is showing.

The exchange return only reaches the app when the association files claim your host (see
[Deep links](#deep-links)). With `mobile_distribution` enabled, configure the app entries in
your application's `identity_settings.mobile_apps` and the platform serves both files for you.

### Your site

While provider sign-in is on, the root element has `data-meroshell-provider-sign-in="on"`,
`MeroFoundryShell.capabilities.providerSignIn` is `true`, and the `meroshell:capabilities`
event fires on `window` whenever that changes. Give each provider button a real link to your
sign-in route, so that it works in a browser as it always has:

```html
<a href="/api/v1/services/<sign-in service id>/inbound?provider=google" data-provider-sign-in="google">Continue with Google</a>
<a href="/api/v1/services/<sign-in service id>/inbound?provider=github" data-provider-sign-in="github">Continue with GitHub</a>
```

```css
/* In the app, show provider buttons only when the shell offers provider sign-in. */
.meroshell:not([data-meroshell-provider-sign-in="on"]) [data-provider-sign-in] { display: none; }
```

Inside the app a click on a `data-provider-sign-in` element with an `href` is taken over: the
shell receives the link and the WebView does not follow it. You can also start sign-in from
script with `MeroFoundryShell.providerSignIn(href)`. It rejects with
`Provider sign-in is not available in this app` while provider sign-in is off, and refuses a
link that is not on your `https://<host>`. Outside the app none of this is installed.

### Known open issue

The platform's OAuth callback checks the browser-binding cookie that the sign-in route set in
the WebView, but the provider returns to that callback inside the system session, whose cookie
jar is separate from the WebView's. The starter does not change or weaken that check, so until
the platform resolves this, provider sign-in from the shell is not known to complete
end to end. The shell side has been tested only against test doubles, never on a device.

## Bundled mode

With `"mode": "bundled"` the app carries your site and calls your application's API from the
device. Remote mode remains the default and is simpler: a new site version reaches users
without a new app build.

- Bring your own static build. `site` names an already-built static site that the starter
  copies as it is. Pages made with the MeroFoundry page builder are rendered by the platform
  at `https://<host>` and cannot be bundled; use remote mode for them.
- Allowed origins. The site is served from `capacitor://localhost` (iOS) and
  `https://localhost` (Android) and calls `https://<host>` cross-origin, so list both in your
  application's allowed origins with `update_application`:
  `{"allowedOrigins": ["capacitor://localhost", "https://localhost"]}`.
- Capability. Bearer sessions need the `mobile_distribution` capability enabled for your
  application; without it a bearer login is refused.
- `MeroFoundryShell.bearer` signs in with a bearer session kept in `MeroFoundryShell.session`:

  ```js
  await MeroFoundryShell.bearer.login('<login model id>', { email, password });
  const response = await MeroFoundryShell.bearer.fetch(`https://${MeroFoundryShell.host}/api/v1/...`);
  const signedIn = await MeroFoundryShell.bearer.signedIn();
  await MeroFoundryShell.bearer.logout('<logout model id>'); // revokes on the server, clears the pair
  ```

  `login` submits the login model with `"session": "bearer"` and `X-Requested-With`, using the
  application id from `https://<host>/api/v1/applications/public/by-host` (never your
  `appId`). `fetch` adds `Authorization: Bearer` only for `https://<host>`; after a `401` it
  refreshes the pair once by body, saves it and retries once. A refused refresh clears the
  pair. Without a saved pair, requests go out unchanged. Nothing is cached, queued or
  refreshed in the background, and no cookie is read.
- Provider sign-in. The provider leg is the one described in
  [Provider sign-in](#provider-sign-in). The validated exchange return gains `session=bearer`
  and is redeemed by native code in the app WebView's cookie context, not loaded as a page.
  The shell saves the pair in secure storage, opens the returned `returnTo` path in your
  bundled site (its root if the path is not a same-origin path) and then fires
  `meroshell:session` on `window` with `detail` `{signedIn: true}` and no token. A refused or
  malformed answer leaves the user on the page they were on.
- Offline. Your bundled site always loads locally. The offline screen appears only when a
  navigation to `https://<host>` fails during a provider sign-in, and **Try again** reloads the
  bundled page the user was on.
- Sign out. **Sign out** removes the saved pair, then the WebView's cookies, and reloads the
  bundled site's root (see [Sign out](#sign-out)).

## Push notifications

The shell receives your application's push notifications natively: APNs on iOS and Firebase
Cloud Messaging on Android, with no JavaScript push plugin. Your site decides when to ask: the
shell never prompts on its own.

### Prerequisites

- Capability. The device routes need the `mobile_distribution` capability enabled for your
  application, the same as bundled mode and provider sign-in. Without it registration fails and
  `enable()` answers `failed`.
- Push credentials. Your application holds its own APNs key and FCM service account, entered once
  as your application's push credentials. MeroFoundry never uses a key of its own.
- iOS. Turn on the Push Notifications capability for your App ID in the Apple Developer portal and
  regenerate the provisioning profiles (`fastlane match`). Create an APNs authentication key
  (.p8) and give MeroFoundry its key id, your team id and your bundle id. `npm run ios:prepare`
  writes `aps-environment` = `development` into `App.entitlements` and adds the two
  `AppDelegate` methods that hand the APNs token to the shell. Development builds register
  with the APNs sandbox. When you archive for TestFlight or the App Store, Xcode signs the
  export with your distribution profile, which sets `aps-environment` to `production`, so
  store builds register with production APNs: set the APNs environment of your push
  credentials to match the build you are testing.
- Android. Create a Firebase project, add an Android app with your `appId` as the package name
  and download its `google-services.json` into `android/app/google-services.json`.
  `android/app/build.gradle` applies the Google services plugin only when that file is
  present. Without it the app still builds and runs, and push answers `unavailable` with
  reason `not_configured`. Give MeroFoundry the Firebase project id and a service account key
  for the FCM HTTP v1 API. Android 13 and later ask the user for the notification permission
  the first time your site turns push on.

### Turn it on from your site

`MeroFoundryShell.push` works the same way in remote and bundled mode. Every method returns a
promise:

```js
const result = await MeroFoundryShell.push.enable();
// {status: 'enabled'} registered for this signed-in user
// {status: 'denied'} the user refused, or turned notifications off in system settings
// {status: 'unavailable', reason} no APNs token, or no google-services.json ('not_configured')
// {status: 'pending', reason: 'session' | 'application'} saved; registers once both exist
// {status: 'failed', reason, httpStatus} the registration request failed
const state = await MeroFoundryShell.push.state(); // {enabled, permission, platform}
await MeroFoundryShell.push.disable(); // {status: 'disabled'} or {status: 'failed', ...}
```

`enable()` asks the operating system for permission only when it has never been answered,
then registers the device with
`PUT https://<host>/api/v1/public/applications/<application id>/push/devices` and the body
`{"data": {"token", "platform", "app_version", "locale"}}`. The platform is `apns` or `fcm`, the
application id is the one the shell reads from `https://<host>/api/v1/applications/public/by-host`,
the app version is the native one and the locale is `navigator.language`. `disable()` deletes the
token on the device first, then sends
`DELETE https://<host>/api/v1/public/applications/<application id>/push/devices/<token>` with the
token URL-encoded.

The registration uses your site's own consumer session. In remote mode the request carries the
page's cookies and `X-Requested-With`; in bundled mode it goes through
`MeroFoundryShell.bearer.fetch`, so it carries the saved bearer pair instead. Call `enable()`
after sign-in. Called before, it answers `pending` and the shell registers by itself once a
session exists: in bundled mode as soon as a sign-in saves a pair, in remote mode on the next
page after sign-in. The device token is never logged, shown, dispatched or stored by the page.

### Renewal

While push is enabled the shell renews the registration when the app starts, at the first page
that loads, and again when the app returns to the foreground a day or more after the last
renewal. A token that the operating system changes is registered the same way. Operations run
one at a time in the order they were called, and `disable()` cancels every registration queued
before it, so a renewal or token change can never register the device again after
`disable()` or sign-out.

### Taps

A notification's `path` (the in-app path set on the push notification) opens when the user taps
it, including the tap that launches the app: the shell waits until the first page has loaded and
then opens the path once. In remote mode it opens `https://<host><path>` exactly like a deep link;
in bundled mode it opens the path in your bundled site. The path must be an absolute path on your
application, starting with one `/`, at most 1024 characters, with no backslash, space or control
character. Any other value never navigates: the shell logs only the reason and fires
`meroshell:push` on `window` once a page is loaded, with `detail`
`{type: 'rejected', reason}` and no path. A notification with no path opens the app where it was.
On iOS a notification that arrives while the app is open shows as a banner; on Android the shell
shows it in the notification shade.

### Sign out and settings

**Sign out** first asks your page to disable push, so the registration is removed with the session
that made it, and only then removes the saved bearer pair or the cookies. It waits at most five
seconds. If the page does not answer in time or the request fails, sign-out continues anyway and
the shell still deletes the token on the device, so nothing renews it. The settings screen shows
**Notifications** as **On** or **Off**. It has no switch: your site turns push on and off.

## App lock

- The lock is off by default. A user turns it on in the app's settings; the shell asks them
  to authenticate before it saves the setting. The setting is stored on the device only.
- When the lock is on, the app shows the lock screen on launch and whenever it returns from
  the background, and your site stays hidden until authentication succeeds. When the user
  cancels or fails, the app stays locked and shows **Unlock** to try again. Too many failures
  defer to the device passcode.
- Face ID, Touch ID, Android biometrics and the device passcode are accepted. On iOS the
  system prompt uses the text "<appName> uses Face ID to unlock the app."
- The lock is independent of the server session: locking does not sign the user out, and
  signing out does not turn the lock off.

## Sign out

**Sign out** in the settings screen first has your page turn push notifications off (see
[Push notifications](#push-notifications)), then deletes every cookie in the app's WebView on this device,
including the application's session cookies, and then reloads `https://<host>/`, which shows
your site signed out. It does not call a server-side logout, so the server forgets the session
when it expires in the normal way. It does not clear the app lock setting or other site data
such as local storage.

In bundled mode **Sign out** first removes the token pair saved in secure storage, then deletes
the WebView's cookies and reloads the root of the bundled site. It does not revoke the session
on the server; `MeroFoundryShell.bearer.logout` does. The settings screen shows **Bundled** or
**Remote** beside the host and never shows a token.

## Deep links

The app claims `https://<host>/...` links. The operating systems only open them in the app
once your host publishes two association files. When the `mobile_distribution` capability is
enabled for your application, list your apps in its `identity_settings.mobile_apps` (an `ios`
entry with team id, bundle id and claimed paths; an `android` entry with package name and
SHA-256 certificate fingerprints) and the platform serves both files ahead of your site.
Otherwise you own these files: put them in your site's `public/.well-known/` folder so that
they are deployed with your site (with GitHub releases, set `include-hidden-files: true` on
the upload step so the dot-folder is included). Provider sign-in needs the same files.

`public/.well-known/apple-app-site-association` (no file extension, served as JSON):

```json
{
  "applinks": {
    "details": [{ "appIDs": ["ABCDE12345.com.example.app"], "components": [{ "/": "/*" }] }]
  }
}
```

Use your Apple team id and your `appId`. Enable the **Associated Domains** capability for
the App ID in the Apple Developer portal and regenerate the match profile once afterwards.

`public/.well-known/assetlinks.json`:

```json
[{
  "relation": ["delegate_permission/common.handle_all_urls"],
  "target": {
    "namespace": "android_app",
    "package_name": "com.example.app",
    "sha256_cert_fingerprints": ["AA:BB:..."]
  }
}]
```

Use the app signing key's SHA-256 fingerprint from the Play Console (Setup, App signing).

A link opened before the app is unlocked loads behind the lock screen. Links to other hosts,
non-HTTPS links and links with credentials or a port are ignored, and so is a link to an OAuth
exchange route: only a sign-in the shell started may load one.

## Release workflows

`.github/workflows/ios.yml` and `.github/workflows/android.yml` run on `workflow_dispatch`
and on tags matching `v*`. Each one first runs the release guard, then installs dependencies,
prepares the native project, generates the artwork and builds. They commit nothing back to the
repository and read no MeroFoundry credential.

### iOS (`ios.yml`, `macos-latest`)

`npm ci` → `npm run web` → `npx cap add ios` → `npx cap sync ios` → `npm run ios:prepare` →
`npm run assets -- --ios` → `bundle exec fastlane ios release`, which reads your signing
material with `match` in **readonly** mode, builds the Release configuration, and uploads the
build to TestFlight. The build number is the workflow run number.

| Secret | Value |
|---|---|
| `APPLE_TEAM_ID` | Your 10-character Apple Developer team id |
| `APP_STORE_CONNECT_API_KEY_ID` | Key id of an App Store Connect API key with the App Manager role |
| `APP_STORE_CONNECT_API_ISSUER_ID` | Issuer id shown with that key |
| `APP_STORE_CONNECT_API_KEY_CONTENT` | The key's `.p8` file, base64-encoded (`base64 -i AuthKey_XXXX.p8`) |
| `MATCH_GIT_URL` | URL of your existing match certificates repository |
| `MATCH_GIT_BASIC_AUTHORIZATION` | base64 of `user:token` with read access to that repository |
| `MATCH_PASSWORD` | The passphrase that encrypts your match repository |

Before the first run you need:

1. An Apple Developer Program membership with two-factor authentication on the account.
2. The App ID (`appId`) registered with the **Associated Domains** capability.
3. Existing match signing material: an App Store distribution certificate and an App Store
   provisioning profile for `appId`, created once on your Mac with `fastlane match appstore`.
   The workflow never creates or changes signing material.
4. The app record created in App Store Connect with the same bundle id, and an App Store
   Connect API key.

### Android (`android.yml`, `ubuntu-latest`)

`npm ci` → `npm run web` → `npx cap sync android` → `npm run assets -- --android` → `./gradlew bundleRelease`
signed with your upload keystore → `r0adkll/upload-google-play` to the **internal** track.
The version code is the workflow run number.

| Secret | Value |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | Your upload keystore, base64-encoded (`base64 -w0 upload.keystore`) |
| `ANDROID_KEYSTORE_PASSWORD` | The keystore password |
| `ANDROID_KEY_ALIAS` | The upload key alias |
| `ANDROID_KEY_PASSWORD` | The upload key password |
| `PLAY_SERVICE_ACCOUNT_JSON` | JSON key of a Google Cloud service account invited in the Play Console with permission to release to testing tracks |

Before the first run you need:

1. A Google Play developer account and the app created in the Play Console with the
   package name `appId`.
2. An upload keystore, with Play App Signing enabled for the app.
3. **One manual upload.** Google Play accepts API uploads only after the first App Bundle has
   been uploaded by hand. Build it locally and upload it to the internal track in the Play
   Console:

   ```sh
   npm run web && npx cap sync android && npm run assets -- --android
   cd android
   ANDROID_KEYSTORE_FILE=/path/to/upload.keystore ANDROID_KEYSTORE_PASSWORD=... \
     ANDROID_KEY_ALIAS=... ANDROID_KEY_PASSWORD=... ./gradlew bundleRelease
   ```

4. The service account above.

## Tests

`npm test` runs the Node test runner over `test/`. It validates the configuration (both
modes), the `www/` assembly and its freshness check, the release guards (including a
preview-sync-then-release fixture and a web-asset lifecycle for each platform), the shell
screens and their controller, the hosted-page integration, pull to refresh (gesture
eligibility, lock suppression and offline recovery, with the native side replaced by a
double), provider sign-in (the capability probe, the sign-in leg, return validation and the
races with cancellation, lock and Custom Tab close, again against doubles; the native
web-authentication code is checked as source text only), push (registration, renewal, the
ordering of enable, refresh and disable, taps and sign-out cleanup, against native and fetch
doubles; the APNs and FCM code is checked as source text only), the generated iOS project after
`npx cap add ios`, the Android project, and both workflow files. The native code (asset paths,
host and mode, the Keychain and EncryptedSharedPreferences session store) is checked as source
text only. It builds no binary, runs no workflow and does not exercise a device.
